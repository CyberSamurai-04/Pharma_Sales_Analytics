Power BI

Turning the same star schema into a live dashboard

The SQL analysis already sits on a fact table and a drug dimension — that shape drops into Power BI with no rework. This page covers the data model, the DAX, and what's actually built so far.

In progress

Built: the import-ready star schema, a proper date dimension, the DAX measures below, and a full build guide. Not yet built: the actual .pbix report pages — that's the next sitting at Power BI Desktop.

01 — Data model

The star schema

Same idea as the SQLite model on the Methodology page — one fact table, two dimensions — generated by powerbi/build_powerbi_extract.py straight from the cleaned CSVs.

FileRowsRole
fact_sales.csv16,848Date, ATCCode, Units
dim_drug.csv8ATCCode, DrugName, DrugGroup
dim_date.csv2,191One row per calendar day, 2014–2019 in full

Relationships: fact_sales[Date] → dim_date[Date] and fact_sales[ATCCode] → dim_drug[ATCCode], both many-to-one.

  • dim_date spans complete calendar years, not just the ~2,106 days with actual sales — Power BI's time-intelligence functions need a contiguous date table, or SAMEPERIODLASTYEAR silently breaks at year boundaries
  • MonthName and WeekdayName are set to sort by their numeric columns in the model, so charts read January → December instead of alphabetically
  • dim_date is marked as the official Date table — required for the DAX below to work at all

02 — DAX measures

Four measures doing what the SQL layer does

Same four questions as the SQL queries — ranking, share of total, year-over-year, and the moving average — written as DAX instead.

Total Units base measure
DAX 
Total Units = SUM(fact_sales[Units])

Everything else in this list builds on this one measure.

% of Total ALL()
DAX 
% of Total =
DIVIDE(
    [Total Units],
    CALCULATE([Total Units], ALL(dim_drug))
)

ALL(dim_drug) removes the category filter but keeps whatever date range is selected — so this reads as "share of the currently filtered period," which is more useful on a dashboard than a fixed denominator.

YoY % SAMEPERIODLASTYEAR()
DAX 
Prior Year Units =
CALCULATE([Total Units], SAMEPERIODLASTYEAR(dim_date[Date]))

YoY % =
DIVIDE([Total Units] - [Prior Year Units], [Prior Year Units])

Only works because dim_date is contiguous and marked as the date table — the same reason the SQL version cuts every year to Jan–Oct instead of comparing full years against a partial 2019.

3M Moving Avg DATESINPERIOD() · SUMMARIZE()
DAX 
3M Moving Avg =
VAR CurrentDate = MAX(dim_date[Date])
VAR TrailingMonths =
    CALCULATETABLE(
        SUMMARIZE(dim_date, dim_date[YearMonth], "MonthlyTotal", [Total Units]),
        DATESINPERIOD(dim_date[Date], CurrentDate, -3, MONTH)
    )
RETURN
    AVERAGEX(TrailingMonths, [MonthlyTotal])

Written from known DAX patterns, not run against the model yet — I couldn't execute DAX to verify it myself. Check it against the SQL version's already-verified numbers: April 2019 ≈ 1,900.0 and September 2019 ≈ 1,563.8 (query 4 on the Methodology page). If it drifts from those, Power BI's native Analytics-pane trend line (set to a 3-period moving average) is a zero-DAX fallback.

03 — Report pages

What the dashboard will show

Three pages, mapped directly to the static charts already on the Results page — except a viewer can filter and drill into them.

Page 1 · Overview

KPI cards, a category ranking bar chart, and slicers for year and drug group — the interactive version of the concentration finding.

Page 2 · Trend

Monthly units against the 3-month moving average, plus the weekday-effect chart from the bonus finding on the Methodology page.

Page 3 · Year-over-Year

A Year × Category matrix with conditional colour formatting — the interactive twin of the static heatmap on Results.
